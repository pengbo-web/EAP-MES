## 2. 模块 4b:OEE 三率计算引擎

### 2.1 现状与缺口
- `mes_eap_device` 只存**最新状态**与最后事件时间,无法做时长积分 → 缺状态变更流水
- 看板"稼动率"目前是 运行台数/总台数 的**瞬时占比**,不是 OEE 时间稼动率
- 理论周期(理想节拍)无任何表承载

### 2.2 数据模型(新增 2 表 + 0 改表)

```sql
CREATE TABLE mes_eap_device_state_log (
  id BIGINT NOT NULL, device_code VARCHAR(64) NOT NULL,
  from_status CHAR(1) DEFAULT NULL COMMENT '变更前 0运行 1报警 2离线',
  to_status   CHAR(1) NOT NULL     COMMENT '变更后',
  event_time  DATETIME NOT NULL,
  tenant_id VARCHAR(20) DEFAULT '000000', del_flag CHAR(1) DEFAULT '0',
  create_dept BIGINT, create_by BIGINT, create_time DATETIME, update_by BIGINT, update_time DATETIME,
  PRIMARY KEY (id), KEY idx_dev_time (device_code, event_time)
) COMMENT='设备状态变更流水(OEE时长积分依据)';

CREATE TABLE mes_eap_device_spec (
  id BIGINT NOT NULL, device_code VARCHAR(64) NOT NULL,
  ideal_cycle_sec DECIMAL(12,4) NOT NULL DEFAULT 0 COMMENT '理论周期(秒/件)',
  planned_minutes INT NOT NULL DEFAULT 480 COMMENT '日负荷时间(分钟)',
  tenant_id VARCHAR(20) DEFAULT '000000', del_flag CHAR(1) DEFAULT '0',
  create_dept BIGINT, create_by BIGINT, create_time DATETIME, update_by BIGINT, update_time DATETIME,
  PRIMARY KEY (id), UNIQUE KEY uk_dev (device_code, tenant_id)
) COMMENT='设备OEE基准参数';
```

### 2.3 代码挂接点
- `EapIntegrationService.touchDevice(...)`:状态**发生迁移**时(含"超过 offline-minutes 视为离线"的查询期推断)插入 state_log;同状态心跳不插
- 新建 `com.liaoyun.mes.eap.MesOeeService` + `MesEapDeviceStateLog`/`MesEapDeviceSpec` 域与 Mapper
- 离线切片:查询时若最后一条流水早于窗口起点且状态非离线,补一条"推断离线"区间(不落库,仅计算期修正)

### 2.4 算法(按设备按日)
```
loadMin   = spec.planned_minutes                          # 负荷时间
runMin    = Σ [state=0 区间] ∩ [当日00:00, 现在]            # 运行时长(跨天切片)
alarmMin  = Σ [state=1 区间] ∩ 当日                         # 报警停机
时间稼动率 A = runMin / loadMin
性能稼动率 P = ideal_cycle_sec × Σcount(当日 work_rec) / (runMin×60)
良率        Q = (Σcount − Σdefective) / Σcount             # 当日该设备报工
OEE = A × P × Q   (各率封顶1.0, 防止理论周期配置错误爆出>100%)
```

### 2.5 接口
- `GET /mes/eap/oee?deviceCode=&date=yyyy-MM-dd` → `{A,P,Q,OEE,runMin,alarmMin,qty,defective}`
- `GET /mes/eap/oee/summary?date=` → 全设备列表 + 工厂级 OEE(产量加权)

### 2.6 验收
1. 插 spec 夹具:4 台设备 ideal_cycle_sec=6, planned_minutes=1440
2. 停桥接器 3 分钟制造离线区间 → 恢复 → 查询当日 OEE,手算 A 对照(误差<1%)
3. 断言:OEE == A×P×Q(接口自洽),各率 ≤ 100%

## 3. 模块 5:SN 双向追溯服务

### 3.1 现状与缺口
- 正向链数据分散:`mes_task(sn)` → `mes_work_rec(task_id)` → `mes_qua_rec(sn,task_id)` → `mes_ycrec(sn)`;但 **work_rec 无设备/参数快照**(EAP 报工的设备与参数现在只写在 remark 文本里,不可检索)
- 反向链:物料批次(`mes_inventory_ledger.sn` 入库流水 / `mes_instock.id`) → `mes_fifo_alloc`(ledger_sn→out_no=订单号) → `mes_outstock(remark1=订单号)` → `mes_work(orderid)` → `mes_task.sn`;**批次级反向**(件级反向需 SN-批次绑定表,超本期范围,文档第 7 节声明边界)

### 3.2 数据模型(改 1 表)
```sql
ALTER TABLE mes_work_rec
  ADD COLUMN device_code VARCHAR(64) DEFAULT NULL COMMENT '报工设备(EAP快照)',
  ADD COLUMN params VARCHAR(500) DEFAULT NULL COMMENT '工艺参数JSON快照(EAP)';
```
`EapIntegrationService.autoReport` 写入两快照字段(报工行自包含,追溯不依赖设备表当前值)。

### 3.3 接口与组装
- `GET /mes/trace/forward/{sn}` 正向(件级):
```json
{"sn":"...","work":{"sn":"工单sn","title":"..."},
 "processes":[{"process":"工序名","device":"DEV-EAP-01","operator":"用户id","count":5,
   "defective":0,"params":"{\"v\":226.6}","time":"...","quality":[{"title":"...","res":"结果为:正常"}],
   "alarms":[{"ycdesc":"...","status":"0待审核"}]}]}
```
 组装:task(sn) → work_rec(task_id, 按 create_time 升序) → proid 关联 `mes_process.title` → qua_rec(task_id) → ycrec(sn)
- `GET /mes/trace/backward/{ledgerSn}` 反向(批次级):
 ledger_sn → fifo_alloc(out_no) → outstock(remark1=out_no) → work(orderid) → `{workSnList, qtyPerWork}` 并附每工单的 task sn 清单
- 性能:依赖现有索引 + 新增 `KEY idx_sn (sn)` on mes_work_rec(task_id 已有);反向链路全部走索引列,不扫全表

### 3.4 验收
1. 对 SN-EAP-DEMO-003 调正向:断言 processes 数组非空、含 device_code 与 params 快照、quality/alarms 子节点存在
2. 取任一 fifo_alloc.ledger_sn 调反向:断言返回包含 SN-EAP-DEMO-003(该批次确实被其出库占用)
3. 未报工过的 sn 调正向:返回空树 + code 200(不报错)

## 4. 模块 6:工序级自动派工规则引擎

### 4.1 现状与缺口
- 工艺路线已存在:`mes_prosetting(proId, processId, sort, workshopId 默认工作站)`
- 工作站能力已存在:`mes_workplaces.processIds`(逗号串)、`equIds`、`counts`(产能/容量)
- 但任务创建靠移动端扫码(`MesMobileController.scando`),**无下达即派工**;报工完工后任务直接关闭,不流转到下一工序

### 4.2 规则定义(可配置,不硬编码)
```
候选集   = workplaces where processIds contains 当前工序id and status=0 and suspend_until < now
负载     = count(mes_task where workplace_id=候选 and status='1')
容量因子 = workplace.counts (null 视为 1)
得分     = 负载 / 容量因子     → 取最小; 平局取 id 升序
无候选   = 回退 prosetting.workshopId; 仍不可用 → 抛业务异常"工序X无可用工作站"
```
新增表:
```sql
CREATE TABLE mes_workplace_suspend (
  id BIGINT NOT NULL, workplace_id BIGINT NOT NULL,
  reason VARCHAR(255), suspend_until DATETIME NOT NULL,
  tenant_id VARCHAR(20) DEFAULT '000000', del_flag CHAR(1) DEFAULT '0',
  create_dept BIGINT, create_by BIGINT, create_time DATETIME, update_by BIGINT, update_time DATETIME,
  PRIMARY KEY (id), KEY idx_wp (workplace_id, suspend_until)
) COMMENT='工作站暂停(报警联动)';
ALTER TABLE mes_task ADD COLUMN workplace_dispatch VARCHAR(64) DEFAULT NULL COMMENT '派工来源:RULE/MANUAL/FALLBACK';
```

### 4.3 触发点与流转改造
1. **下达派工**:`POST /mes/dispatch/release/{workId}`
   - 读 prosetting(sort 升序)→ 取首工序 → 规则选工作站 → 建 `mes_task`(sn=工单sn+流水, currproid=首工序, workplace_id=选中, status='1', workplace_dispatch='RULE')
2. **报工流转**:`EapIntegrationService.autoReport` 完工分支改造:
   - 若 prosetting 中存在 sort 更大的下一工序 → task.currproid/currprocess 推进、workplace_id 按规则重选、status 保持 '1'(流转而非关闭)
   - 末工序完工 → task.status='2'、工单 okprocess 推进(沿用现逻辑)
3. **报警改派**:`autoAlarm` 增加:事件 device → 其所在工作站(equIds 包含 device 或当前 task.workplace)写 `mes_workplace_suspend`(默认 30 分钟,可配)→ 该站 status='1' 的任务按规则**改派**到次优候选(workplace_dispatch='RULE',remark 追加改派痕迹)
4. 查询:`GET /mes/dispatch/plan/{workId}` 返回各工序候选工作站得分明细(面试演示规则透明性)

### 4.4 验收
1. release 工单 9005(新夹具,prosetting 2 工序、每工序 2 个候选工作站预置不同负载)→ 断言首任务落在低负载站
2. 发 PROCESS_COMPLETE → 断言 task.currproid 推进到工序 2 且 workplace 按规则重选、status='1'
3. 发 PARAM_ALARM(device 属于当前站)→ 断言 suspend 行存在、在途任务改派、得分明细接口显示该站被排除
4. 末工序完工事件 → task.status='2'、work.okprocess+1

## 5. 实施顺序与工时

| 序 | 模块 | 工时 | 依赖 |

| 1 | OEE 引擎(2 表 + state_log 挂接 + 2 接口) | 2d | 一期 touchDevice |
| 2 | 追溯(work_rec 加 2 列 + 2 接口) | 2.5d | 一期 autoReport |

| 合计 | | 7.5d | 每模块独立 commit、独立验收 |

风险与对策:
- autoReport/autoAlarm 被三个模块共用 → 改造顺序 OEE→追溯→派工,每步跑一期既有回归(桥接器活链 + verify_mrp/verify_fifo 脚本)防回归
- 派工改造触碰任务状态机 → 保留开关 `eap.dispatch.enabled`(默认 true,关闭时回退一期"完工即关闭"语义)

## 7. 简历回写与面试边界清单

六条终态措辞(全部"已实测"口径):
1. EAP-MES 集成:事件驱动自动报工、报警转待审核单、网关密钥通道、租户/数据权限处理
2. MRP:递归 N 层展开 + 循环保护 + 净需求,实测 4 层
3. FIFO:批次级分配 + 扣减行批次回填,替换库位级存储过程
4. 看板 + OEE:设备状态流水积分三率、稼动率/良品率/进度/小时趋势大屏
5. 追溯:件级正向树(含设备与参数快照)+ 批次级反向(声明件级反向为边界)
6. 派工:能力匹配 + 负载最短规则引擎,报警联动暂停改派,报工驱动工序流转

边界话术(自研 vs 作者):
- 自研:`com.liaoyun.mes.{eap,mrp,fifo}` 四包 + 本文档三模块 + 6 张新表/3 列 ALTER + 部署改造
- 作者:基础 CRUD、移动端报工页、原看板 8081、vue 前端(有登录页布局缺陷,已记录)
- 每个自研模块备一句"为何不用原实现":FIFO 原为库位级且丢批次号;MRP 原硬编码三层且 float;报工原为扫码人工;看板原为作者外部 8081 服务
